# Skill: bug-fix

角色：Senior Engineer，执行 regression-driven bug fix——先写失败测试，再修复，确保每个 bug 修复都带回归测试。

**前置条件**：`/triage` 已完成分析（根因、风险、置信度、TDD 计划）。本技能只负责执行。如果直接调用且没有 triage 上下文，先快速执行 triage Phase 1-2（定位根因 + 风险评估）再继续。

## 触发条件

**USER TRIGGER**：`/bug-fix` 或 `/bug-fix:walkthrough`。通常由 `/triage` 路由到这里。
**AUTO TRIGGER**：`/triage` 分类为 Bug 后自动路由。
**DO NOT TRIGGER**：用户只说「调查」「为什么」「查原因」（调查阶段不触发）。

## 调用模式

- `/bug-fix` — 默认模式：先红后绿
- `/bug-fix:walkthrough` — 交互模式：适合 UI 状态机、多步交互流程等复杂 bug

---

## 核心哲学

将每个 bug 视为技术债的信号，而非孤立的错误去打补丁。不要添加条件判断或"创可贴式"逻辑来处理这个具体症状——退一步，识别允许这种状态存在的底层架构弱点（泄漏的抽象、错误的状态所有权、过度耦合等）。提供能将代码库推向"理想状态"的重构方案，优先追求优雅的简洁性与健壮性，从设计上消除这一类问题，而不仅仅是压制它。

---

## 模式路由

1. 用户说 `/bug-fix:walkthrough` 或 bug 涉及 **UI 多步交互、状态机、多组件联动** → 执行 **交互模式**
2. 其他 → 执行 **默认模式**
3. 判断不确定时 → 问用户

---

## 默认模式

### 核心原则

**先红后绿：任何代码修复之前，必须先有一个因该 bug 而失败的测试。**

不允许跳过测试直接改代码。测试既是 bug 存在的证据，也是修复正确的证明。

### Phase 1：编写失败测试（红）

使用 `/triage` 的 TDD 计划（或自行设计，若直接调用）：

1. **选择测试位置**：
   - 按本仓库的测试目录约定放（看项目 CLAUDE.md / 现有 tests 布局），后端、前端、pipeline 各放各的层
2. **命名规范**：`test_bug_<简短描述>` 或 `test_regression_<简短描述>`
3. **测试内容**：
   - 构造触发 bug 的最小输入/场景
   - 断言**预期的正确行为**（不是断言错误行为）
   - 添加注释说明这是哪个 bug 的回归测试
4. **运行测试，确认它失败（红）**：
   - 用本仓库的测试命令跑单个用例（如 `pytest <file>::<name> -v`、`npx vitest run <file> -t "<name>"`，按项目实际环境调整）
5. **向用户展示测试失败输出**，确认失败原因确实是目标 bug（而非测试本身写错）

**关键检查**：如果测试直接通过了，说明：
- 测试没有正确复现 bug（重写测试）
- 或者 bug 描述/理解有误（回到 triage 重新确认）

### Phase 2：修复 Bug（绿）

1. **结构性修复，不打补丁**：
   - 先问自己：这个 bug 暴露了什么设计缺陷？（状态所有权错位、抽象泄漏、职责混杂、缺少不变量保护等）
   - 修复应消除**产生 bug 的条件**，而不是在症状处加 `if` 判断 / 特殊分支 / fallback
   - 如果正确的修复需要移动逻辑到更合适的位置、收紧接口、拆分职责——就做，这不是「顺手重构」，这是修复的一部分
   - 如果根因在上游（调用方传了不该传的值、数据在更早的阶段就错了），修上游，不要在下游兜底
   - 修复完后回顾：「如果有人再犯同类错误，这个修复能防住吗？」如果不能，说明还在打补丁
2. 运行刚才写的测试，确认通过（绿）
3. 运行相关的完整测试套件，确认没有引入新问题：
   - 用本仓库的测试命令跑相关目录/全量（同上，按项目实际环境）

### Phase 3：汇报

向用户报告：
- **根因**：一句话说明 bug 原因（来自 triage 或自行分析）
- **修复**：改了什么，为什么这样改
- **结构性检查** ✅/❌：修复是否消除了产生 bug 的条件（而非仅压制症状）？如果答案是「加了一个特殊判断来绕过」，标记 ❌ 并说明为什么没做结构性修复（时间/风险/范围限制），让用户决定是否接受
- **测试**：新增了哪个测试，覆盖了什么场景
- **验证**：测试结果（从红到绿）

## 交互模式（`/bug-fix:walkthrough`）

适用于：UI 状态机 bug、多步交互流程 bug、多组件联动 bug——这类 bug 的「期望行为」往往不明确或有争议，直接写测试容易写偏。

### 核心原则

**先对齐行为，再锁定测试，再写修复。** 测试来源于用户确认的交互流程，不是 AI 从代码推导的。

### Phase 1：交互式走查（核心差异）

逐步引导用户走一遍涉及 bug 的操作流程。用户扮演操作者，AI 描述每一步的屏幕状态，用户确认或纠正。

**执行方式：**

1. **设定场景**：描述初始状态（几条数据、什么身份、哪个页面），让用户确认起点。
2. **逐步推进**：每一步描述：
   - 用户做了什么操作（点击、输入、快捷键）
   - 屏幕应该变成什么样（哪些元素出现/消失/变化）
   - 明确列出 UI 元素状态（展开/折叠、按钮文字、文案内容）
3. **等用户确认**：每步之后等用户说「对」或纠正。不要一口气列完所有步骤。
4. **覆盖分支**：走完 happy path 后，主动提出异常/边界场景（失败、空状态、并发），同样逐步确认。
5. **记录决策**：用户纠正的地方是最重要的信息——记住这些纠正，它们定义了「真正的期望行为」。

**产出**：一份步骤列表，每步有明确的「操作 → 期望 UI 状态」，用户已逐条确认。

### Phase 2：写集成测试（锁定行为）

从 Phase 1 的步骤列表直接翻译为集成测试。

1. **每个确认过的步骤 → 一个或一组测试**，测试名直接引用步骤编号（如 `Step 3: ERP rejection → row stays expanded`）
2. **断言用户看到的东西**：DOM 元素存在/不存在、文案内容、回调是否触发——不断言内部状态
3. **参考现有模式**：仓库里已有的走查产出集成测试（如有）是范例
4. **运行测试**：预期部分失败（红），这些失败就是要修的 bug
5. **向用户展示**：哪些步骤的测试通过了（行为已正确），哪些失败了（需要修）

### Phase 3：修复（绿）

1. 针对失败的测试逐个修复代码
2. 每修一处，运行对应测试确认变绿
3. 全部绿后，跑完整测试套件确认无回归

### Phase 4：浏览器验证

提示用户在浏览器中走一遍 Phase 1 确认过的流程，对照每一步检查。

---

## 不要做的事

- ❌ 不要在测试通过前修改非测试代码
- ❌ 不要写「测试 bug 存在」的测试（如 `assert result is None`），要写「测试正确行为」的测试
- ❌ 不要把回归测试混入已有的不相关测试函数里——新建独立测试函数
- ❌ 不要为了让测试通过而降低断言标准
- ❌ 不要跳过测试说「我先修了再补测试」——顺序不能反
- ❌ （交互模式）不要从代码推导期望行为——期望行为来自用户确认，代码现状可能就是错的
- ❌ （交互模式）不要一口气列完所有步骤——逐步推进，等用户确认

## 示例：测试命名与结构

```python
# tests/unit/test_bug_duplicate_order_submit.py

def test_bug_duplicate_order_on_rapid_submit():
    """回归测试：快速连续点击提交按钮导致订单重复创建。

    根因：提交接口没有幂等保护，前端 debounce 在某些场景下失效。
    """
    order_data = make_order(...)
    result1 = submit_order(order_data)
    result2 = submit_order(order_data)
    assert result1.status == "created"
    assert result2.status == "duplicate"
```

```typescript
// 交互模式产出的集成测试（来自用户确认的步骤列表）
// frontend/src/__tests__/integration/ReviewStateMachine.test.tsx

it('Step 3: ERP rejection → row stays expanded, 跟进 button hidden', async () => {
  // Setup: row 1 submitted, row 2 pending — ERP will reject row 2
  // ...
  // KEY: row stays expanded (no auto-collapse) — user confirmed this in walkthrough
  expect(getExpandedRowCount()).toBe(1);
  expect(isFooterVisible()).toBe(false);
});
```

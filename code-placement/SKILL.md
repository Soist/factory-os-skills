# Skill: code-placement

角色：Code Placement & Abstraction Guard — 代码放置、职责边界与抽象完整性守卫。

## 触发条件

**USER TRIGGER**：用户说「检查架构」「代码该放哪」「检查抽象泄漏」「architecture check」「leaky abstraction」，或调用 `/code-placement`。
**AUTO TRIGGER**：Claude 创建新文件、在模块间移动逻辑、或新增跨层调用时，自动评估放置合理性。
**DO NOT TRIGGER**：小范围编辑现有文件内部逻辑时不触发。

---

## 核心指令

在放置任何逻辑之前，评估整个系统以找到**最稳健的位置**（函数、类或模块），而非最顺手的位置。同时检查是否存在**泄漏的抽象**——调用者绕过抽象层直接依赖实现细节的模式。

不要简单地追加到第一个看起来相关的文件；考虑这段逻辑是否属于：
- 一个专用 utility
- 特定的 service 层
- 需要一个新的抽象来维持干净、反脆弱的架构

如果当前结构有缺陷，或者添加这段代码会造成泄漏抽象，**在继续之前指出并建议正确的重构**。

---

## 维度一：代码放置评估

对每次代码放置，回答以下问题：

1. **职责归属**：这段逻辑的核心职责是什么？系统中哪个模块/层级对此负责？
2. **复用性**：这段逻辑是否会被多处调用？如果是，它是否应该是共享 utility？
3. **依赖方向**：放在这里是否引入了不合理的依赖（如底层模块依赖上层）？
4. **抽象边界**：是否破坏了现有模块的抽象边界？调用者是否需要知道不该知道的内部细节？
5. **一致性**：项目中类似的逻辑放在哪里？新代码是否遵循同样的模式？
6. **可测试性**：放在这里是否让单元测试变得困难（如深度耦合、需要 mock 大量依赖）？

---

## 维度二：抽象泄漏检测

扫描指定范围的代码，找出调用者绕过抽象层直接依赖实现细节的模式。

泄漏的抽象 = 上层代码做了本应由下层封装的决策。这导致：
- 同一决策散布在多处（变更时要改 N 个地方）
- 上层与具体实现耦合（换实现要改调用方）
- 代码意图被 if/else 分支掩盖

### 检测模式

1. **`isinstance` / 类型检查绕过多态**
```python
# BAD: 调用者检查具体类型来决定行为
if isinstance(self.backend, TencentCOSBackend):
    self.backend.upload(path, cached_key=key)
else:
    self.backend.upload(path)

# GOOD: 统一接口，子类各自实现
result = self.backend.upload(path)  # 多态分派
```

2. **环境/配置分支散布在业务层**
```python
# BAD: service 层根据部署环境做 if/else
if storage_config.use_cos:
    url = upload_to_cos(path)
else:
    url = f"/images/{basename}"

# GOOD: 工厂/组合根决定一次，之后走统一接口
url, _ = uploader.upload(path)
```

3. **抽象接口签名不统一**：子类方法参数 ⊋ 基类方法参数，调用者被迫知道哪个子类支持哪些参数。

4. **属性/方法仅某个实现有**，调用者通过 `hasattr`/`getattr` 探测。

5. **同一个 if/else 在多处重复**：`if config.X` 出现在 2+ 个不同函数/文件中做类似分支，说明缺少封装层。

### 合法例外（不报告）

- 工厂函数 / 组合根（`get_default_*()`, `create_*()`, DI 容器）
- 测试代码中的 mock 和断言
- 序列化/反序列化边界
- 日志/可观测性中的额外上下文探测

## 执行流程

1. **搜索**：用 Grep 在目标范围搜索上述模式
2. **过滤**：排除合法位置
3. **分析**：对每个命中，判断调用者是否必须知道这个实现细节
4. **报告**：

### 放置问题输出

- **当前放置**：代码将被放在哪里
- **问题**：为什么这不是最佳位置
- **建议放置**：应该放在哪里，以及为什么
- **需要的重构**：最小改动

### 泄漏问题输出

| 文件:行号 | 模式 | 泄漏描述 | 严重度 | 建议修复 |
|-----------|------|---------|--------|---------|

严重度：
- **高**：同一分支在 3+ 处重复，或暴露安全/资源管理细节
- **中**：2 处重复，或破坏抽象边界但尚可控
- **低**：单处，但不符合项目约定

如果当前放置合理且无泄漏，简要说明理由即可。
